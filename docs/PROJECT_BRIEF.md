# 项目简介 · 书房 Shufang（作品集用）

## 30 秒介绍
书房是一个帮助人“把阅读沉淀成长期思考”的读书笔记产品。每本书只有一条按时间排列的笔记流，用四种笔记（摘录 / 观点 / 思考 / 行动）区分内容性质；AI 教练只提问不代写，AI 自动建议概念标签把不同书里的想法串起来；邮箱登录、实时云端保存，支持中英文和多种导出。

## 背景与问题
- 我自己读书后“不知道写什么”，笔记写完就沉底，几个月后无法回看当时的想法。
- 市面上的读书工具偏“摘录收集”，缺少引导思考和跨书连接的机制。

## 目标用户
想长期坚持深度阅读的个人：知识工作者、学生、写作者、做研究的人。

## 解决方案（产品形态）
1. 书架：在读 / 读完 / 想读差异化呈现 + 搜索 + 按开始 / 读完时间筛选 + 每日回看旧想法。
2. 笔记流：摘录、观点、思考、行动四类笔记；观点可标立场；纸质书可拍照摘录并识别文字。
3. AI 教练：针对整本书或某条观点追问，每题单独回答；记得过往回答，不重复提问。
4. 概念标签：AI 建议、人确认；回顾页按概念和时间线汇集想法。
5. 数据：邮箱登录、实时同步、Word / PDF / 图片 / Markdown / JSON 导出。
6. 免注册体验示例：面向招聘方和朋友的零门槛试用，预置示例数据（含 AI 教练的问答示例），不消耗 AI 额度。

## 关键产品决策与取舍
| 决策 | 为什么 | 取舍 |
|---|---|---|
| 把十几个并列板块收成“一条笔记流 + 四种类型” | 用户每次都在纠结“该写在哪”，认知负担大 | 失去了固定模板的“完整感”，换来写作的低门槛 |
| 用“原话 → 转述 → 判断 → 行动”区分类型 | 与《如何阅读一本书》“先理解、再评论”的思路一致，类型之间有性质差异而不是位置差异 | 摘录类型固定、不可与其他类型互转（因为带原文和页码） |
| AI 教练只提问、不代写 | 目标是逼用户思考，代写会削弱思考 | 体验不如“一键生成总结”惊艳，但更符合产品初衷 |
| 概念标签“建议 + 一键确认” | 手写 `[[ ]]` 门槛太高；全自动又会污染用户内容 | 多一次点击，换来可控和可信 |
| AI 触发做成门槛式（字数、停顿、轻量模型、可关闭） | 控制成本和打扰 | 极短的笔记不会得到建议 |
| 界面里不暴露“功能是怎么设计的”说明 | 说明文字是设计没做好的补丁 | 需要靠命名、状态和空状态引导做好 |
| 提供免注册示例模式（预置数据、关闭 AI） | 展示场景下，对方不愿意注册，也不该消耗我的 AI 额度 | 看不到真实 AI 响应，所以用预置的教练问答来示意 |
| 本地缓存 + 云端同步，每本书一行、最近修改优先 | 保证写作不被网络打断，同时数据不丢 | 多设备同时编辑同一本书可能覆盖 |

## AI 设计要点
- **角色约束：** 教练提示词明确“只提问、不总结、不夸奖”；按用户立场分流提问策略（不同意/存疑 → 追问依据；同意 → 追问边界；未表态 → 追问是否同意）。
- **上下文：** 带上全书简介、用户的思考、其他书里的相关想法，以及最近 3 组问答（避免重复）。
- **成本与安全：** 概念标签使用轻量模型并设字数 / 停顿门槛；API key 只在服务器端，函数校验登录并按邮箱白名单放行，未配置白名单时一律拒绝。
- **语言一致性：** 界面语言切到英文时，教练指令整体改为英文，避免指令互相矛盾。

## 技术架构
单文件原生 JS 前端（无构建）→ Supabase（邮箱魔法链接登录、Postgres + RLS、私有 Storage）→ Netlify Function 转发 Anthropic API。详见 README。

## 我学到的
- 产品简化比加功能更难：每一次“这两个板块很像”的反馈，都对应一次信息架构的收敛。
- AI 功能的边界设计（只提问、人确认、可关闭、可停止）比模型本身更影响信任感。
- 用户反馈里的“奇怪”常常是定位不清，而不是样式问题。
